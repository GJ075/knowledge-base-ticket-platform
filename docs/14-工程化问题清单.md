# 14 系统工程化审查与问题清单

> 日期：2026-11-11
> 范围：`server/`、`web/`、`embed/`、`infra/`、`tools/`、`docs/`
> 目的：按「工程化、可维护」标准找差距，给出优先级与整改路线。不含功能需求评审。

## 1. 结论摘要

功能完成度高：认证、RBAC、RAG、文档审批、工单状态机、评测、回收站都已闭环，依赖版本固定，迁移齐全，前端类型检查通过。

但工程化程度不够：

- **没有任何自动化测试、CI、lint/格式化配置**；
- 当前工作区有 22 个已修改文件和一批未跟踪文件（检索 v2、精排、结构切分、评测配置），尚未形成可交付基线；
- 运行中的容器已包含未提交代码和迁移 0008，**代码、数据库、提交记录三者不一致**；
- 多处静默降级与重复配置，排障成本高；
- 文档与代码出现漂移，且存在重号文档。

问题按优先级分为 P0（阻断交付）、P1（可维护性）、P2（规范）。

## 3. P0：阻断交付的问题

### P0-1 仓库根目录存在可用登录令牌

`cookies.tmp` 是 curl 的 cookie 文件，内含 `access_token` JWT：

```text
#HttpOnly_localhost ... access_token eyJhbGc...
```

风险：任何人拿到该文件即可在有效期内冒充领导。虽然文件未跟踪，但 `git add -A` 会把它提交。

措施：

1. 删除 `cookies.tmp`、`corpus.tmp`；
2. 轮换 `JWT_SECRET`，使旧令牌立即失效；
3. `.gitignore` 增加 `*.tmp`、`cookies*`、`.vscode/`；
4. 检查历史提交中是否有类似文件。

### P0-2 零自动化测试、零 CI

当前所有回归依赖 [08-首版测试手册](08-首版测试手册.md) 人工执行。评测系统本身也需要被测试，否则无法判断检索改动是否造成退化。

措施（按投入排序）：

1. 后端：pytest + httpx，对工单状态机、文档审批、评测执行器做服务层测试；
2. 前端：vitest 测工具函数与 hooks，Playwright 覆盖登录、问答、工单、评测四条主路径；
3. CI：`ruff check`、`tsc --noEmit`、`pytest`、`next build` 四项作为合并门槛。

### P0-3 精排阈值在未启用精排时被错误应用

[retrieval.py:243](../server/app/services/retrieval.py)

```python
if config.rerank_threshold > 0:
    candidates = [item for item in candidates if item.score >= config.rerank_threshold]
```

`score` 在精排关闭时是 RRF 融合分（约 0.01–0.03），与 0–1 的精排阈值不可比。只要配置了阈值但忘记开精排，检索结果会被全部过滤，表现为「知识库有内容却永远拒答」。

措施：阈值只在 `rerank_enabled` 且精排成功后生效；或在配置层强制校验「阈值 > 0 必须开精排」。

### P0-4 迁移 0008 未回填全文索引，混合检索对旧分块静默失效

`0008_retrieval_v2` 只新增 `content_tsv`、`content_hash` 等列，没有回填。旧分块的 `content_tsv` 为 NULL，稀疏召回只能覆盖重新索引过的文档；`retrieval.search` 在稀疏召回异常时直接降级，不记录日志（见 P1）。

措施：

1. 明确「升级 0008 后必须执行 `scripts/reindex_all.py`」，并写入迁移说明与 README；
2. 检索时统计 `content_tsv IS NULL` 的分块数量，超过阈值时记录告警日志；
3. 评测报告记录「索引版本」，避免拿旧索引结果与新索引结果对比。

### P0-5 评测策略无法在页面配置

后端已支持 `POST /eval/datasets/{id}/runs` 传 `retrieval_config`，但数据集页只展示配置摘要，没有选择入口；想对比 dense / hybrid / rerank 只能手写 curl。这与「用评测驱动检索优化」的目标不匹配。

措施：

1. 预设下拉：稠密 / 混合 / 混合+精排 / 自定义；
2. 高级参数（candidate_k、fused_k、阈值）做范围校验；
3. 运行报告展示配置全量，对比页按配置分组。

### P0-6 文档重号与文档漂移

- `docs/` 下同时存在 `13-文档批量删除与回收站设计.md` 与 `13-检索优化设计.md`；索引只收录前者。
- [04-API接口设计](04-API接口设计.md) 未记录 `retrieval_config`、引用新增的 `heading_path`/`score` 字段。
- [02-总体架构设计](02-总体架构设计.md)、README 仍写「800 字切分、100 重叠」，代码已改为 450/700/60。

措施：重编检索设计为 14、工程审查为 15；更新索引；把「接口/配置变更必须同步文档」写入交付定义。

### P0-7 单队列单 Worker，评测会阻塞文档入库

`celery_app` 只有一个默认队列，`index_document` 与 `run_evaluation` 共用 worker。一次 20 条评测可能持续数分钟，期间上传文档一直 `pending`。任务也没有 `time_limit`、`acks_late` 配置。

措施：拆分 `ingest` 与 `eval` 两个队列，分别启动 worker；为两类任务设置软/硬超时与重试策略。

### P0-8 安全基线缺失

| 项 | 证据 | 建议 |
|---|---|---|
| JWT 默认密钥 | [config.py:23](../server/app/core/config.py) `change-me-in-env` | 启动时校验非默认值，生产强随机 |
| 登录无限流 | 无 slowapi/限流中间件 | 按 IP + 用户名限速，失败锁定 |
| 登录页预填密码 | [login/page.tsx:13](../web/app/login/page.tsx) | 移除预填（已知问题 003） |
| 种子默认密码 | `scripts/seed.py` | 首次登录强制改密或生产禁用 |
| 无 CSRF token | 依赖 SameSite=Lax | 生产加 CSRF 或 BFF |

### P0-9 运行态与版本不一致

未提交代码已经部署，迁移 0008 已执行。此时若回滚代码到上一个提交，数据库结构会与模型不匹配；若继续开发，又没有可回滚的基线。

措施：先提交当前 v2 检索（或打 tag），再做后续改动；迁移一旦上线视为不可回滚，降级脚本只用于本地。

## 4. P1：可维护性问题

### 4.1 巨型服务与巨型页面

| 文件 | 行数 |
|---|---|
| `server/app/services/eval_service.py` | 1099 |
| `server/app/services/ticket_service.py` | 1042 |
| `server/app/services/document_service.py` | 895 |
| `web/app/(main)/evaluations/[id]/page.tsx` | 731 |
| `web/app/(main)/tickets/[id]/page.tsx` | 726 |
| `web/app/(main)/evaluations/runs/[id]/page.tsx` | 579 |

一个文件承担查询、校验、事务、状态机、序列化五种职责，修改时回归面过大。建议按「查询 / 命令 / 校验 / 输出」拆分，页面抽取 hooks（选择、批量操作、轮询）与子组件。

### 4.2 静默降级与宽泛异常

全仓 33 处 `except Exception`，其中以下几处没有任何日志：

- [retrieval.py:231](../server/app/services/retrieval.py)：稀疏召回失败直接丢弃 BM25 结果；
- [retrieval.py:263](../server/app/services/retrieval.py)：精排失败回退融合顺序（有日志但无指标）；
- `document_service` 删除 MinIO 对象失败只记 warning。

建议统一降级策略：记录结构化日志 + 计数器，评测报告标注「本次运行发生过降级」，否则会把基础设施故障误判为检索质量下降。

### 4.3 N+1 与查询性能

- `list_datasets` 每个数据集执行 3 次查询（用例数、轮次数、最近运行）。
- `list_runs` 每条运行额外查数据集和用户各一次。
- 文档/回收站搜索使用 `ILIKE '%kw%'`，无 `pg_trgm` 索引；数据量上千后全表扫描。
- 工单列表多条件筛选只有单列索引，缺少 `(status, created_at)` 等复合索引。

### 4.4 配置重复与校验缺失

`RetrievalConfig` 与 `Settings` 各维护一份同名默认值，新增参数要改两处；`_merge_retrieval_config` 对类型转换失败直接忽略，非法阈值会被静默丢弃，用户以为配置生效。

### 4.5 硬编码与语义偏差

- `RRF_K=60`、`MERGE_MAX_CHARS=1200`、token 估算 `0.7` 写死在代码里；
- `within_budget` 超预算时用 `continue` 而非 `break`，结果可能超出预算；
- `merge_adjacent` 合并后未更新 `token_count`，后续预算计算失真。

### 4.6 评测与业务语料未隔离

`documents.source` 字段已新增，但上传接口不接收、前端不展示，所有文档仍写 `internal`。公开测试集导入后会进入同一知识库，污染日常问答引用。

### 4.7 前端缺少错误边界与路由级状态

没有 `app/error.tsx`、`not-found.tsx`、`loading.tsx`；任一页面渲染异常会整页白屏。所有页面均为客户端取数，首屏无数据骨架之外的降级。

### 4.8 类型契约靠手写同步

`web/lib/types.ts` 与后端 Pydantic 模型人工对齐，已出现 `retrieval_config` 只在后端存在的情况。建议用 OpenAPI 生成 TS 类型，CI 校验差异。

### 4.9 可观测性不足

- 请求日志没有 `user_id`，无法按用户排查；
- Celery 任务没有把 `request_id` 传下去，日志无法串联；
- 没有指标（检索耗时、精排耗时、LLM 失败率、队列积压）与告警。

### 4.10 回收站与存储增长

回收站长期保留分块与对象，没有保留天数、容量统计或清理任务；361 篇测试文档产生的数据会一直占用存储与向量索引。

### 4.11 容器与部署

- Dockerfile 未创建非 root 用户，运行时镜像包含 `build-essential`；
- compose 没有 `restart` 策略、资源限制、日志轮转；
- api 启动时自动执行 `alembic upgrade`，多副本部署会并发迁移。

## 5. P2：规范与体验

1. 后端已有 ruff 配置但未安装/未执行；前端无 eslint、prettier，代码风格靠人工。
2. 依赖已固定版本（优点），但没有 `pip-audit`/`npm audit` 等漏洞扫描。
3. Python 版本三处不一致：宿主机 3.13、api 3.12、embed 3.11，文档未说明原因与限制。
4. 一次性脚本散落在 `/tmp`，未纳入 `tools/` 或 `scripts/` 管理。
5. 缺运维手册：备份与恢复、扩容、故障排查、迁移演练。
6. API 无版本化与废弃策略，客户端升级没有缓冲期。
7. 评测指标没有显著性说明，小样本差异容易被误读为策略优劣。

## 6. 建议整改路线

| 阶段 | 时间 | 内容 |
|---|---|---|
| 0 止血 | 1–2 天 | 删除临时文件、轮换 JWT、`.gitignore` 补全；提交 v2 检索；搭 CI 骨架（lint + typecheck + compile + smoke） |
| 1 修 P0 | 3–5 天 | 修阈值逻辑；明确 0008 回填/重索引流程；评测页加策略选择与校验；重编文档并同步；拆 Celery 队列；安全基线 |
| 2 结构治理 | 1 周 | 拆分三大 service 与三个巨型页面；消除 N+1；补索引；统一异常与降级日志；补错误边界 |
| 3 可运维 | 1 周 | 指标与告警、备份恢复演练、保留策略、发布与回滚流程、依赖与安全扫描 |

## 7. 工程化达标定义（Definition of Done）

- 每次合并自动执行 lint、类型检查、单元测试、构建，全部通过；
- 核心路径（登录、问答、文档审批、工单流转、评测运行）有自动化用例；
- 数据库迁移有升级与回滚演练记录，回填类迁移有明确操作步骤；
- 所有配置项有默认值、范围校验与文档说明；
- 接口、数据模型、前端类型三者由同一契约生成或自动校验；
- 关键链路有指标与日志，可在 5 分钟内定位一次失败；
- 有备份恢复与故障处理手册，且演练过；
- 无高危依赖漏洞、无凭据与令牌进入仓库。

## 8. 值得保留的做法

- 依赖版本全部固定，可复现构建；
- Alembic 迁移按编号递进，历史清晰；
- 统一错误码与 JSON 日志；
- 前端 TypeScript 严格模式、零 `any`；
- 评测系统把「运行快照、指标、基线对比」做进了数据模型，这是后续检索优化最重要的基础设施。
