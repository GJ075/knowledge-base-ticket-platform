# 11 开发过程问题记录

本文单独记录开发、联调和环境搭建过程中实际遇到的问题，与 [10-已知问题](10-已知问题.md) 中的产品缺陷（001–008）分开。本文的问题大多已经解决或已绕过，保留下来便于换机、重建环境或交付部署时快速排查。

## 1. 环境与启动问题

### E01 Docker 拉取镜像失败，报 oauth token 获取超时

| 项 | 内容 |
|---|---|
| 现象 | `failed to solve: failed to fetch oauth token ... dial tcp 202.160.130.66:443: connectex: A connection attempt failed` |
| 原因 | 本机通过 FlClash（`127.0.0.1:7890`）访问外网，但 Docker Desktop 没有使用该代理；Docker 拉镜像不走系统代理。 |
| 处理 | Docker Desktop → Settings → Resources → Proxies 配置手动代理 `http://127.0.0.1:7890`，重新拉取成功。`docker info` 中显示内部代理属于正常现象。 |
| 状态 | 已解决（环境配置） |

### E02 宿主机端口被已有项目占用

| 项 | 内容 |
|---|---|
| 现象 | 启动 Compose 时报 `port is already allocated`，5432 / 6379 / 9000 / 9001 被本机已有 `kb-*` 项目占用。 |
| 原因 | 本机同时存在另一个知识库项目，使用相同默认端口。 |
| 处理 | 本项目宿主机映射改为 PostgreSQL `5433`、Redis `6380`、MinIO `9010/9011`；容器内部端口不变，服务间仍通过 `postgres:5432` 等通信。旧项目未改动。 |
| 状态 | 已解决（环境配置） |

### E03 Worker 启动报缺少 packaging

| 项 | 内容 |
|---|---|
| 现象 | Worker 启动失败：`ModuleNotFoundError: No module named 'packaging'` |
| 原因 | Celery / Kombu 运行时依赖 packaging，但镜像中没有显式安装。 |
| 处理 | `server/requirements.txt` 增加 `packaging==24.2`，重建 worker。 |
| 状态 | 已解决（依赖） |

### E04 Worker 报 Redis transport 版本不匹配

| 项 | 内容 |
|---|---|
| 现象 | `VersionMismatch: Redis transport requires redis-py >= 6.1, please install redis or increase the versions` |
| 原因 | Kombu 版本与 redis-py 版本不匹配。 |
| 处理 | 固定 `kombu==5.7.0`，升级 `redis==6.1.0`。 |
| 状态 | 已解决（依赖） |

### E05 VS Code / 终端无法识别 npm

| 项 | 内容 |
|---|---|
| 现象 | PowerShell 中执行 `npm run dev` 报 `无法将“npm”项识别为 cmdlet...`；`npm -v` 同样失败，但完整路径 `& "C:\Users\Lenovo\AppData\Local\nodejs\npm.cmd" -v` 可以运行。 |
| 原因 | 本机 Node 位于 `C:\Users\Lenovo\AppData\Local\nodejs`；系统检查显示该目录的 Target 指向 Claude 桌面应用包缓存下的 `LocalCache\Local\nodejs`。用户 PATH 虽然包含该目录，但 VS Code 及其父进程仍持有旧环境；集成终端继承旧 PATH，命令解析找不到 `npm.cmd`。 |
| 处理 | 1）临时用完整路径启动；2）当前终端用注册表数据刷新 PATH；3）在 VS Code 用户设置中增加 `terminal.integrated.env.windows`，把 nodejs 目录前置到 Path，保证新终端可用。 |
| 状态 | 已绕过（VS Code 配置）；换机或重装后建议用标准方式安装 Node，并重新登录系统刷新环境 |

### E06 Next.js 安全告警

| 项 | 内容 |
|---|---|
| 现象 | `npm install` 提示 Next.js 15.1.0 存在安全告警。 |
| 原因 | 初始版本存在已知安全公告。 |
| 处理 | 升级到 `next@15.5.29`，`npm run build` 通过。 |
| 状态 | 已解决（依赖） |

### E07 电脑重启后 Docker 服务不完整

| 项 | 内容 |
|---|---|
| 现象 | 重启后只有 postgres / redis / minio 恢复运行，api / worker / embedding 处于 Exited 状态，前端也无法访问后端。 |
| 原因 | Docker Desktop 重启后未自动恢复全部容器；前端 dev server 也已退出。 |
| 处理 | 启动 Docker Desktop 后执行 `docker compose up -d api worker embedding`，并重新启动 `npm run dev`。 |
| 状态 | 已解决（环境恢复） |

### E08 前端 dev server 退出码 4

| 项 | 内容 |
|---|---|
| 现象 | 后台运行 `npm run dev` 的进程以 exit code 4 退出，3000 端口不可访问。 |
| 原因 | 环境重启 / 终端会话结束后 dev server 被终止，并非代码编译错误。 |
| 处理 | 重新执行 `npm run dev`，确认 `/login` 返回 200。 |
| 状态 | 已解决（环境恢复） |

## 2. 开发中已修复的代码问题

### C01 登录成功后仍停留在登录页

| 项 | 内容 |
|---|---|
| 现象 | 输入正确账号密码后接口 200，但页面不跳转。 |
| 原因 | `AuthProvider.login` 和登录页的 `useEffect` 同时触发导航，产生重复跳转。 |
| 处理 | 移除 `AuthProvider.login` 中的 `router.push`，只保留登录页在 `user` 变化后跳转 `/chat`。 |
| 状态 | 已修复 |

### C02 Celery 任务报 asyncpg “attached to a different loop”

| 项 | 内容 |
|---|---|
| 现象 | 文档索引任务在 worker 中失败：`Future ... attached to a different loop`。 |
| 原因 | Celery 每个任务运行在独立事件循环，而全局 async 引擎的连接池跨循环复用。 |
| 处理 | 每个任务使用新建的 `create_async_engine(..., poolclass=NullPool)` 和独立 session factory，任务结束 `engine.dispose()`。 |
| 状态 | 已修复 |

### C03 文档更新 / 重新索引报 MissingGreenlet

| 项 | 内容 |
|---|---|
| 现象 | 更新或重新索引接口返回 500，日志为 `MissingGreenlet`，访问 `updated_at` 时触发。 |
| 原因 | commit 后服务端生成的 `updated_at` 已过期，序列化时触发异步懒加载。 |
| 处理 | commit 后通过 `_load_document` 重新查询并返回。 |
| 状态 | 已修复 |

### C04 工单操作成功后返回的处理人 / 时间线是旧数据

| 项 | 内容 |
|---|---|
| 现象 | 审核、指派等操作成功，但响应里的 `assignee` 为 null、时间线缺少刚写入的事件，前端需要手动刷新。 |
| 原因 | commit 后对象关系仍使用会话内旧状态。 |
| 处理 | 统一使用 `_respond_after_commit`：commit 后 `expire` 并重新查询工单，再序列化。 |
| 状态 | 已修复 |

### C05 `_respond_after_commit` 自身报 MissingGreenlet

| 项 | 内容 |
|---|---|
| 现象 | 在 C04 的修复中，commit 后访问 `ticket.id` 触发 `MissingGreenlet`。 |
| 原因 | `ticket.id` 在 expire 后也处于过期状态，重新查询需要先拿到主键。 |
| 处理 | commit / expire 前先缓存 `ticket_id = ticket.id`，再用主键重新查询。 |
| 状态 | 已修复 |

### C06 解析文本未清洗导致 PostgreSQL 拒绝写入

| 项 | 内容 |
|---|---|
| 现象 | `phase1-sample.pdf` 解析成功，但写入 `document_chunks` 时报 `invalid byte sequence for encoding "UTF8": 0x00`，文档标记为 `failed`。 |
| 原因 | PDF 提取文本中混入 NUL 字节和其他控制字符，`parse_document` 未清洗，PostgreSQL 的 `text` 类型拒绝 NUL。 |
| 处理 | 新增 `server/app/services/text_cleaner.py` 的 `sanitize_text`，统一清理 NUL/C0/C1 控制字符、孤立代理字符、BOM、零宽字符、bidi 控制和解码替换符；`parse_document` 与 `chunk_text` 入口调用；TXT 解码改为 `utf-8-sig + errors="replace"`。 |
| 验证 | 失败的 `P1 PDF Test` 重新索引后 `ready`，4 个分块无非法字符；含多种控制字符的 TXT 索引正常。详见 [10-已知问题](10-已知问题.md) 001。 |
| 状态 | 已修复 |

### C07 DOCX 等 OOXML 文件 MIME 被存成 application/octet-stream

| 项 | 内容 |
|---|---|
| 现象 | `.docx` 上传后 `documents.mime_type` 为 `application/octet-stream`，下载响应也是该类型。 |
| 原因 | 文档上传只按文件名调用 `mimetypes.guess_type`；Python 内置表不含 `.docx`，Linux 容器又没有 `/etc/mime.types`，上传时的 `content_type` 未被采用。 |
| 处理 | 新增 `server/app/services/mime_types.py` 显式映射 pdf/doc/docx/xls/xlsx/ppt/pptx/odt/ods/odp/md/markdown/txt/csv；文档上传使用 `guess_mime_type`，工单附件使用 `resolve_mime_type`；历史 DOCX 记录已回填。 |
| 验证 | 客户端故意传 `application/octet-stream` 时，文档与工单附件仍得到正确 DOCX MIME；下载 `Content-Type` 正确，字节一致。详见 [10-已知问题](10-已知问题.md) 002。 |
| 状态 | 已修复 |

### C08 补录事件被 ticket_events 的 CHECK 约束拒绝

| 项 | 内容 |
|---|---|
| 现象 | 补录工单创建时返回 500，日志为 `CheckViolationError: new row for relation "ticket_events" violates check constraint "ck_ticket_events_action"`。 |
| 原因 | `ck_ticket_events_action` 的允许值列表没有包含新增的 `backfilled`，模型和数据库约束不同步。 |
| 处理 | 更新模型约束，并新增迁移 `0004_backfilled_event` 重建 CHECK 约束，加入 `backfilled`。 |
| 验证 | 补录创建、审核、驳回、修改后审核全部通过，事件正常写入。 |
| 状态 | 已修复 |

### C09 失败补偿 helper 被误改成递归调用

| 项 | 内容 |
|---|---|
| 现象 | 制造一次工单号冲突后，日志出现 `database rollback failed` 和 `RecursionError: maximum recursion depth exceeded`，MinIO 对象没有被清理。 |
| 原因 | 批量替换 `await db.rollback()` 时，把 `_safe_rollback` 函数体本身也替换成了 `await _safe_rollback(db)`，形成无限递归，导致回滚失败、后续存在性检查失败，从而跳过对象清理。 |
| 处理 | 恢复 helper 内部为 `await db.rollback()`，回滚异常只记录类型和消息，不再输出可能递归的完整堆栈；重新验证冲突后计数器回滚、对象清理正常。 |
| 状态 | 已修复 |

## 4. 维护说明

- 新增开发过程问题时，优先判断属于环境、依赖、测试工具还是产品缺陷。
- 产品缺陷统一记录在 [10-已知问题](10-已知问题.md)，本文只记录开发与联调过程。
- 换机或重建环境时，按 E01–E08 逐项检查可以减少重复踩坑。
