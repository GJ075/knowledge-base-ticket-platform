# 07 开发阶段与验收标准

## 1. 开发原则

1. **先主体框架，后完善**：每个阶段交付一个能启动、能演示的最小闭环。
2. **不追求检索准确率**：首版只验证"上传 → 检索 → 回答 → 引用"链路通了，不调优。
3. **用户测试驱动迭代**：我完成代码，不做深入测试和精修；你按测试手册测试，把问题记录下来，再按优先级完善。
4. **每阶段可独立验收**：阶段之间不堆积未验证的大块功能。
5. **设计先行**：本文档和 01–06 经你确认后才开始编码。

## 2. 阶段总览

| 阶段 | 目标 | 主要交付物 | 依赖 |
|---|---|---|---|
| Phase 0 | 脚手架与基础设施 | 目录、Compose、迁移、健康检查、登录 | 无 |
| Phase 1 | 文档入库与审批 | 上传、解析、切分、embedding、审批 | Phase 0 |
| Phase 2 | RAG 问答 | 检索、DeepSeek、SSE、引用、历史 | Phase 1 |
| Phase 3 | 工单 | 状态机、权限、附件、事件、列表详情 | Phase 0 |
| Phase 4 | 前端联调 | 全部页面、角色化 UI、端到端流程 | Phase 1–3 |
| Phase 5 | 交付与测试手册 | 启动说明、测试用例、已知限制 | Phase 4 |

## 3. 阶段详情

### Phase 0：脚手架与基础设施

**目标**：项目能一键启动，能登录，健康检查通过。

**交付物**：

- `server/`、`embed/`、`web/`、`infra/`、`scripts/` 目录骨架。
- `infra/docker-compose.yml`：postgres、redis、minio、embedding、api、worker。
- `.env.example` 与配置加载。
- Alembic 初始迁移：扩展、表、索引、序列。
- 种子脚本：1 领导 + 2 员工。
- 认证接口：登录、退出、当前用户。
- 健康检查：`/health/live`、`/health/ready`。
- 前端登录页与基础布局。

**验收标准**：

1. `docker compose up -d` 后核心容器健康。
2. `/health/ready` 返回 database、redis、minio、embedding 均为 ok。
3. 领导、员工账号均可登录，错误密码返回 401。
4. 未登录访问受保护接口返回 401。
5. 前端登录后进入 `/chat`，退出后回到 `/login`。

**测试重点**：环境启动、账号、Cookie、健康检查。

### Phase 1：文档入库与审批

**目标**：文档能上传、解析、切分、向量化，并可通过审批流程控制。

**交付物**：

- MinIO 文档桶与上传。
- `documents`、`document_changes`、`document_chunks` 表与接口。
- PDF / DOCX / Markdown / TXT 解析。
- 固定长度切分（默认 800 字、100 字重叠）。
- embedding 服务与批量向量化。
- Celery 索引任务、索引状态更新、失败重试。
- 文档列表、详情、下载、重新索引。
- 员工新增/修改/删除变更审批；领导直接生效。
- 文档审批页面接口。

**验收标准**：

1. 领导上传 PDF，文档状态从 `pending` → `indexing` → `ready`。
2. 文档分块与向量写入数据库。
3. 员工上传后生成待审批变更，审批前不可检索。
4. 领导通过后文档入库并可检索；驳回后不生效。
5. 员工修改文档，审批期间旧版本仍可检索；通过后新版本生效。
6. 员工删除文档，审批期间仍可检索；通过后文档和分块被删除。
7. 不支持的类型或超过 50MB 返回明确错误。
8. 索引失败时状态为 `failed`，领导可重新索引。

**测试重点**：四种文件格式、审批三种动作、索引状态、错误输入。

### Phase 2：RAG 问答

**目标**：完成"提问 → 检索 → 生成 → 引用"闭环，先不管准确率。

**交付物**：

- `conversations`、`messages` 表与接口。
- `POST /chat/stream` SSE 接口。
- 问题向量化、pgvector top-5 检索。
- DeepSeek 流式生成。
- 引用列表写入助手消息。
- 多轮上下文（最近 5 轮）。
- 无结果拒答话术。
- 会话列表、会话详情、删除会话。
- 前端问答页、历史页。

**验收标准**：

1. 提问命中知识库时，前端逐字显示回答，并展示引用。
2. 引用包含文档名和片段。
3. 提问知识库没有的内容时，返回固定拒答话术。
4. 多轮追问能利用上一轮上下文。
5. 会话历史只对本人可见；领导看不到员工历史。
6. 断流或 LLM 错误时，前端显示错误并可重试。

**测试重点**：SSE、引用、多轮、拒答、历史隔离。

### Phase 3：工单

**目标**：员工工单和领导工单的全部状态路径可走通，权限正确。

**交付物**：

- `tickets`、`ticket_attachments`、`ticket_events` 表与接口。
- 工单创建（员工 → `new`，领导 → `pending_assignment`）。
- 全部状态动作：approve、reject、assign、complete、modify-complete、confirm、edit。
- 乐观锁 `version`。
- 附件上传、下载、删除。
- 工单列表、筛选、详情、时间线。
- `available_actions` 计算。
- 角色和数据范围校验。

**验收标准**：

1. 员工工单完整路径：`new → in_progress → completed → resolved`。
2. 员工工单回退路径：`new → returned → modified → in_progress → …`。
3. 员工工单终审回退：`completed → returned → modified → in_progress → …`。
4. 领导工单路径：`pending_assignment → in_progress → pending_user_confirmation → resolved`。
5. 领导工单未解决：`pending_user_confirmation → returned → modified → in_progress → …`。
6. 非法状态转换返回 409；越权返回 403。
7. 版本冲突返回 409，前端刷新后重试成功。
8. 员工只能看自己提交的和指派给自己的；领导看全部。
9. 工单时间线记录每个动作。
10. 附件可上传、下载、删除；非 `returned` 状态不能改附件。

**测试重点**：状态机全路径、权限矩阵、并发版本、附件。

### Phase 4：前端联调

**目标**：所有页面可用，员工和领导各走一遍端到端流程。

**交付物**：

- 问答、历史、文档、文档审批、工单列表、新建工单、工单详情页面。
- 角色化导航和按钮。
- SSE 流式渲染、上传下载、审批弹窗、时间线。
- 401/403/409 的统一处理。
- 骨架屏、空状态、错误状态。

**验收标准**：

1. 员工登录后看不到"文档审批"入口。
2. 领导登录后能看到全部工单和文档审批入口。
3. 员工上传文档、领导审批、问答引用全流程可完成。
4. 员工提交工单、领导审核指派、员工处理、领导终审全流程可完成。
5. 刷新页面后登录态保持；退出后受保护页面不可访问。
6. 409 冲突有明确提示并可恢复。

**测试重点**：端到端流程、角色可见性、错误提示。

### Phase 5：交付与测试手册

**目标**：用户可以按手册独立启动和测试，问题可复现、可记录。

**交付物**：

- 最终版 `docs/08-首版测试手册.md`（补充实际命令、端口、账号）。
- 根目录 `README.md` 启动说明。
- 种子数据说明。
- 已知限制清单。
- 问题记录模板。

**验收标准**：

1. 按 README 能从零启动系统。
2. 按测试手册能覆盖全部首版功能。
3. 每个失败用例都能记录：编号、步骤、预期、实际、日志/截图。
4. 已知限制写清楚，不把"未实现"误判为 bug。

## 4. 首版交付定义

### 4.1 算完成

- 所有首版功能已接线，主流程可走通。
- 系统能按 README 启动。
- 健康检查通过。
- 测试手册可用。
- 已知限制有记录。

### 4.2 不算完成

- 检索准确率、回答质量调优。
- UI 视觉精修、动画、响应式细节。
- 边界条件和异常路径的穷举。
- 性能压测、并发压测。
- 生产部署、HTTPS、监控、备份。

这些留到测试反馈后的迭代。

### 4.3 代码底线

- 类型标注、模块边界清晰。
- 配置来自环境变量，不硬编码密钥。
- 统一错误码和日志。
- 不在代码里写死测试账号密码（种子脚本可用环境变量覆盖）。
- 不提交 `.env`、模型文件、上传文件。

## 5. 与测试手册的关系

1. 我完成代码后，你按 [08-首版测试手册](08-首版测试手册.md) 逐项测试。
2. 每个问题按统一模板记录：
   - 用例编号
   - 前置条件
   - 操作步骤
   - 预期结果
   - 实际结果
   - 截图或日志
3. 问题按优先级处理：
   - P0：系统无法启动、主流程阻断。
   - P1：核心功能错误、权限漏洞。
   - P2：次要功能错误、提示不清。
   - P3：体验、文案、样式。
4. 每轮修复后，回归相关用例和受影响路径。

## 6. 建议节奏

不承诺具体日期，建议按以下顺序推进：

1. Phase 0 完成后先让你启动一次，确认环境和登录没问题。
2. Phase 1 完成后先测文档入库和审批，再进入问答。
3. Phase 2 完成后测试问答闭环，不纠结准确率。
4. Phase 3 完成后按状态机逐条测试工单。
5. Phase 4 完成后做员工/领导双角色端到端。
6. Phase 5 汇总问题，进入第一轮迭代。

## 7. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Docker GPU 直通失败 | embedding 慢 | Phase 0 先验证；失败则 CPU 模式继续 |
| BGE-M3 模型下载失败 | 无法索引 | 提前检查网络；必要时离线模型目录 |
| PDF 解析效果差 | 检索内容缺失 | 首版接受；测试时记录，后续换解析器 |
| DeepSeek 网络不稳定 | 问答失败 | 超时、错误码、重试；必要时切换本地模型 |
| 范围蔓延 | 首版延期 | 严格执行 01 的"首版不包含"清单 |
| 设计与实现不一致 | 返工 | 状态机、API、数据模型变更必须同步更新文档和测试用例 |

## 8. 变更管理

- 需求变更先改 01，再改 02–06 中受影响的部分。
- 工单状态机变更必须同步改 05、04、08。
- 数据模型变更必须提供 Alembic 迁移，不允许手改数据库。
- 每轮迭代在 `docs/00-文档索引.md` 记录版本和变更。
