## 001 PDF 提取文本含 NUL 字节导致索引失败

| 项 | 内容 |
|---|---|
| 严重级别 | P1 |
| 状态 | 已修复（2026-11-10） |
| 发现阶段 | Phase 1 实测 B1 |
| 影响模块 | 文档解析 / 索引 |

**现象**

上传 `phase1-sample.pdf` 后，文档 `index_status` 变为 `failed`，分块未写入。

**Worker 日志**

```text
asyncpg.exceptions.CharacterNotInRepertoireError:
invalid byte sequence for encoding "UTF8": 0x00
```

**原因**

`parse_document` 直接使用 `pypdf` 提取的文本，没有清理 `\x00`；写入 `document_chunks.content` 时 PostgreSQL 拒绝非法 UTF-8 字节。

**修复（已实施）**

新增 `server/app/services/text_cleaner.py`：

- `sanitize_text` 清理 NUL、C0/C1 控制字符（保留 `\n`、`\t`）、孤立代理字符、BOM、零宽字符、bidi 控制字符和解码替换符 `U+FFFD`；
- 统一 `\r\n` / `\r` / Unicode 行分隔符为 `\n`，最后做 NFC 归一化；
- `server/app/services/document_parser.py` 的 `parse_document` 在返回前调用清洗；
- `chunk_text` 入口再调用一次，防御直接调用；
- 纯文本解码从 `utf-8 + errors="ignore"` 改为 `utf-8-sig + errors="replace"`，先保留 BOM/非法字节痕迹再统一清洗。

**验证结果**

- `P1 PDF Test` 重新索引：`failed → ready`，生成 4 个分块，分块中无非法控制字符。
- 含 `\x00`、`\x01`、`\x07`、`\x1f` 和零宽空格的 TXT：索引 `ready`，分块内容为“第一段正文，含控制字符。第二段 制表符和 零宽空格。结尾。”
- 说明：该 PDF 文本层本身可读性较差（字体映射问题），现在不会阻断索引，但检索质量仍受原文质量影响，属于后续解析器优化范围。

**保留的测试数据**

- 文档：`P1 PDF Test`，索引状态现为 `ready`
- 文件：项目根目录 `phase1-sample.pdf`

## 002 DOCX MIME 类型被存成 application/octet-stream

| 项 | 内容 |
|---|---|
| 严重级别 | P2 |
| 状态 | 已修复（2026-11-10） |
| 发现阶段 | Phase 1 实测 B1b |
| 影响模块 | 文档 MIME 识别 |

**现象**

上传 `.docx` 后，`documents.mime_type` 为 `application/octet-stream`，而不是 Word 的 MIME 类型。

**原因**

服务端只使用 `mimetypes.guess_type(filename)`。Python 内置表不含 `.docx`，而容器里没有 `/etc/mime.types`；上传请求里的 `content_type` 又未被采用，最终回退到 `application/octet-stream`。

**修复（已实施）**

- 新增 `server/app/services/mime_types.py`：
  - `MIME_BY_SUFFIX` 显式覆盖 `.pdf`、`.doc`、`.docx`、`.xls`、`.xlsx`、`.ppt`、`.pptx`、`.odt`、`.ods`、`.odp`、`.md`、`.markdown`、`.txt`、`.csv`；
  - `guess_mime_type`：显式映射 → `mimetypes` → `application/octet-stream`；
  - `resolve_mime_type`：显式映射 → 清洗后的客户端 `content_type` → `guess_mime_type`；
  - 客户端类型会去掉 `charset` 等参数，并忽略空值、`application/octet-stream`、超长或格式非法的值。
- `document_service._store_file` 改用新的 `guess_mime_type`。
- `ticket_service` 的创建工单附件、追加附件改用 `resolve_mime_type`。
- 历史 `documents` / `document_changes` 中的 `.docx` 记录已回填正确 MIME。

**验证结果**

- 文档上传时客户端故意传 `application/octet-stream`：数据库、接口响应、下载 `Content-Type` 均为正确的 DOCX MIME；下载字节与原文件一致。
- 工单附件同样传 `octet-stream`：附件 MIME 正确。
- `P1 DOCX Test` 已从 `application/octet-stream` 回填为正确 MIME。

**说明**

已有 MinIO 对象上的元数据没有回写；下载接口以数据库字段为准，因此下载类型已正确。若需要 MinIO 控制台也显示正确类型，需要重新上传或复制对象替换元数据。

**保留的测试数据**

- 文档：`P1 DOCX Test`，索引状态 `ready`
- 文件：项目根目录 `phase1-sample.docx`

### 003 登录页预填领导账号和密码

| 项 | 内容 |
|---|---|
| 严重级别 | P2（安全 / 易用） |
| 状态 | 已知，暂不修复（用户决定） |
| 发现阶段 | Phase 3 UI 实测 |
| 影响模块 | 登录页 |

**现象**

打开 `/login` 时，用户名已预填 `leader`，密码已预填 `Leader@123`；直接点击「登录」即以最高权限账号进入系统。

**原因**

`web/app/login/page.tsx:12-13` 将预置账号写入组件初始状态：

```tsx
const [username, setUsername] = useState("leader");
const [password, setPassword] = useState("Leader@123");
```

**影响**

- 任何能打开登录页的人都能一键进入领导账号，生产环境不可接受。
- 员工登录前必须先手动清空领导账号，属于明显的易用性问题。

**建议修法（未实施）**

用户名、密码初始值改为空字符串；演示账号只以文字提示展示，不预填密码；如需保留 demo 便利，可用环境变量仅在开发环境启用。

### 004 期望完成时间允许早于当前时间

| 项 | 内容 |
|---|---|
| 严重级别 | P3（校验） |
| 状态 | 已修复（2026-11-10），并扩展为补录历史工单功能 |
| 发现阶段 | Phase 3 UI 实测 |
| 影响模块 | 新建工单 / 补录工单 / 后端校验 |

**原现象**

创建工单时选择早于当前的时间仍可提交成功。实测工单 `T20261109-000018` 创建于 2026-11-09，期望完成时间为 2026-11-06。

**修复方案**

正常新建工单必须晚于当前时间；需要记录过去时间时，使用新增的「补录历史工单」模式。

**补录规则**

- 员工可以补录自己的工单；领导可以补录任意员工的工单，提交人由领导选择。
- 补录工单创建后状态为 `new`，由领导审核；审核通过直接变为 `resolved`，不进入处理中。
- 审核不通过进入 `returned`，提交人可以编辑、增删附件、标记修改完成，领导再次审核通过后变为 `resolved`。
- 补录可以填写原创建时间（`backfill_created_at`），保存到工单 `created_at`；不填写则使用当前时间。
- 补录的期望完成时间允许是过去时间；普通新建的期望完成时间必须晚于当前时间。
- 编辑已有工单不强制未来时间，避免历史工单因时间已过无法修改。

**实现位置**

- 数据库：`tickets.is_backfilled`，迁移 `0003_ticket_backfill`；事件动作 `backfilled`，迁移 `0004_backfilled_event`。
- 后端：`ticket_service.create_ticket` 增加补录参数与校验；`approve_ticket` 对补录工单直接置为 `resolved`；`_available_actions` 增加补录分支。
- 接口：`POST /tickets` 增加 `is_backfilled`、`backfill_created_at`、`submitter_id`。
- 前端：新建页增加「补录历史工单」开关、原创建时间和提交人选择；列表与详情显示「补录」徽标；时间线显示「补录工单」。

**验证结果**

- 普通新建过去期望时间：前端日期控件拦截，后端返回 422「期望完成时间必须晚于当前时间」。
- 员工补录自己：创建成功，状态 `new`，提交人正确，原创建时间与过去期望时间保存正确；领导通过后 `resolved`。
- 领导代员工2补录：提交人为员工2，员工2可见但无权审核；领导通过后 `resolved`。
- 补录驳回 → 编辑 → 标记修改完成 → 领导通过：最终 `resolved`。
- 补录原创建时间为未来：422「原创建时间不能晚于当前时间」。
- 前端完整流程：领导代员工补录、员工补录自己均走通，详情显示补录徽标和时间线。
- 后端回归 26 项全部通过。

### 观察项（非阻断）

1. 附件增删不改变 `version`，也不写时间线事件。并发场景下，其他用户持有的旧版本号在附件变化后仍然有效；时间线中也没有附件变更记录。首版可接受，若需要完整审计需补事件并递增版本。
2. 回退后再次「标记处理完成」，处理说明输入框会预填上一次的处理说明。若用户未注意直接提交，可能带入旧说明，建议预填为空或明确提示。
3. 并发冲突（409）时，详情页会在后台刷新为最新状态，但操作弹窗保持打开，需要用户手动关闭；错误提示「工单已被更新，请刷新后重试」正常显示。
4. 列表接口对非法的 `status` / `type` / `priority` 筛选值返回 200 和空列表，而不是 422。属于宽松处理，不影响正常 UI（下拉框只会产生合法值）。

### 通过项摘要

- 员工新建（中文、类型、优先级、期望时间、附件）→ 详情展示正确，附件可下载。
- 员工列表权限隔离：只显示本人创建或被指派的工单；其他员工直接访问详情返回「工单不存在」。
- 员工列表筛选：状态、类型、关键字、日期范围、分页、重置均正常。
- 领导列表可看全部工单，处理人筛选、分页正常。
- 领导初审通过并可改派处理人；员工工单进入「处理中」。
- 员工工单：处理完成 → 领导终审驳回 → 员工编辑 / 增删附件 / 标记修改完成 → 领导审核通过 → 再次完成 → 领导终审通过 →「已解决」。
- 领导工单：提交 →「待分配」→ 指派 →「处理中」→ 完成 →「待用户确认」→ 确认未解决（必填原因）→「回退员工修改」→ 修改 → 审核通过 → 完成 → 确认已解决。
- 驳回、确认未解决在未填写原因时确认按钮禁用；员工端在待用户确认状态无可执行操作。
- 并发冲突：两个领导会话同时操作同一工单，后提交方收到 409，页面刷新到最新状态。
- 客户端校验：标题为空提交时停留在新建页并提示「标题和描述不能为空」。

| 影响模块 | 新建工单、新建文档、编辑文档、附件上传、工单编号、MinIO 上传补偿 |

**原现象**

`tickets.title`、`documents.title`、`documents.filename`、`ticket_attachments.filename` 在数据库均为 `varchar(255)`，但创建接口使用未限制长度的 `Form(...)`；前端也没有 `maxLength`。超过 255 字符时会触发 PostgreSQL 的 `StringDataRightTruncationError`，返回 500，甚至连接被重置。

**复现记录**

| 输入 | 修复前 |
|---|---|
| 工单标题 255 字符 | 201 成功 |
| 工单标题 256 字符 | 500 |
| 工单标题 500 字符 | 连接被重置 |
| 文档标题 256 字符 | 500 |
| 文档文件名 300 字符 | 连接被重置 |
| 工单附件名 300 字符 | 数据库错误 + 连接重置，MinIO 留下孤儿对象 |

**修复（已实施）**

1. 长度校验：
   - `POST /tickets` 的 `title` 使用 `Form(min_length=1, max_length=255)`；
   - 文档创建/更新的 `title` 同样限制 255；
   - `validate_upload` 限制文档文件名不超过 255；
   - `_validate_attachment` 限制附件名不超过 255；
   - `create_ticket` / `create_document` / `update_document` 在 service 层再次检查标题长度；
   - 前端新建工单、编辑工单、文档上传/编辑的标题输入框增加 `maxLength={255}`。
2. 工单号不再使用 `nextval` 序列，改为事务型计数表 `ticket_no_counters`（迁移 `0005_ticket_no_counter`）：按 UTC 日期建行，`INSERT ... ON CONFLICT DO UPDATE ... RETURNING` 在业务事务内取号；插入失败回滚时序号一起回滚，不再产生空洞。迁移会把已有工单的最大序号回填到计数表。
3. MinIO 失败补偿：
   - 创建工单时先校验全部附件，再上传 MinIO，记录已上传对象；拿到工单号后写库；
   - 写库失败时回滚事务，用独立查询确认工单未落库后删除已上传对象；
   - 追加附件、文档创建、文档更新同样在提交失败时回滚并删除新对象；
   - 文档删除改为先提交数据库，再删除 MinIO 对象，避免“数据库仍有记录但文件已删除”；
   - 删除失败只记录日志，不掩盖主流程。
4. 数据库异常统一响应：新增 `DBAPIError` 处理器，返回 500 和 `{"error":{"code":"DATABASE_ERROR","message":"数据库操作失败，请稍后重试"}}`，不再出现连接被重置。

**验证结果**

- 工单标题 255 → 201；256/500 → 422，且不消耗工单号；
- 文档标题 256、文档文件名 300、工单附件名 300 → 422，附件失败不写 MinIO；
- 人为制造工单号唯一冲突：接口返回 500 `DATABASE_ERROR`，计数器回滚、工单未落库、MinIO 对象已清理；
- 连续创建 A、C：编号为 `M+1`、`M+2`，中间失败请求没有造成空洞；
- 正常工单流程与文档上传/审批/索引/删除冒烟全部通过；
- 清理后无未被数据库引用的 MinIO 对象。

**说明**

- 已有历史工单号不回改；计数表从已有最大序号继续。
- 极少数“数据库已提交但客户端收到网络错误”的情况无法完全判定，代码在清理前会重新查询工单是否存在，存在则保留对象，避免误删已提交的数据。

### 006 工单列表日期筛选按 UTC 解释，UTC+8 下偏移 8 小时

| 项 | 内容 |
|---|---|
| 严重级别 | P2（数据筛选错误） |
| 状态 | 已修复（2026-11-10） |
| 影响模块 | 工单列表日期筛选、时间参数解析 |

**原现象**

前端把日期筛选拼成不带时区的字符串：

```ts
if (dateFrom) params.set("date_from", `${dateFrom}T00:00:00`);
if (dateTo) params.set("date_to", `${dateTo}T23:59:59`);
```

后端接收为 naive `datetime`，直接与 `timestamptz` 列比较。数据库会话时区为 `Etc/UTC`，因此选择“2026-11-10”实际过滤范围是当地 2026-11-10 08:00 到 2026-11-11 07:59，当地 0:00–7:59 的工单会漏掉。

**修复（已实施）**

1. 前端日期筛选改为发送带时区的 UTC 时间：
   - `date_from`：当地 00:00:00 转 ISO UTC；
   - `date_to`：当地 23:59:59.999 转 ISO UTC。
2. 后端增加 `BUSINESS_TIMEZONE` 配置，默认 `Asia/Shanghai`：
   - 无时区的时间参数按业务时区解释，再转 UTC；
   - 带时区的时间参数直接转 UTC；
   - 用于工单列表日期筛选、`expected_at` 创建/编辑、补录原创建时间。
3. `server/requirements.txt` 增加 `tzdata`，保证 IANA 时区数据可用。

**验证结果**

把工单创建时间设为当地 `2026-11-10 00:30`（UTC `2026-11-09 16:30`）：

| 查询 | 结果 |
|---|---|
| 无时区 `2026-11-10T00:00:00` ~ `23:59:59` | total=1，正确包含 |
| 无时区 `2026-11-09T00:00:00` ~ `23:59:59` | total=0，正确排除 |
| 带 Z 的 UTC 范围 `2026-11-09T16:00:00Z` ~ `2026-11-10T15:59:59Z` | total=1 |
| 带 Z 的 UTC 范围 `2026-11-08T16:00:00Z` ~ `2026-11-09T15:59:59Z` | total=0 |

前端实测请求：

```text
date_from=2026-11-09T16:00:00.000Z
date_to=2026-11-10T15:59:59.999Z
```

另验证无时区 `expected_at=2030-01-01T00:00:00` 按业务时区保存为 UTC `2029-12-31T16:00:00Z`。

### 008 问答 SSE 遇到 401 不触发统一登录跳转

| 项 | 内容 |
|---|---|
| 严重级别 | P3（会话过期体验） |
| 状态 | 已知，暂不修复 |
| 影响模块 | 问答页 |

**现象**

Phase 4 已为 `apiFetch` 增加 401 → `auth:unauthorized` → 跳转登录的统一处理，但 `web/lib/sse.ts` 使用原生 `fetch` 调用 `/chat/stream`，401 时只通过 `onError` 展示「请求失败（401）」，不会跳转登录页。

**建议修法（未实施）**

在 `streamChat` 的 `!response.ok` 分支中，遇到 401 时同样派发 `auth:unauthorized` 事件。

### 观察项（非阻断）

1. 文档和工单附件的下载接口返回 `expires_in: 600`，但实际是普通鉴权 URL，没有签名或过期机制，`expires_in` 只是展示字段。
2. 问答页侧栏只请求 `/conversations` 默认第一页（最多 20 条），超过 20 条的会话只能在「我的历史」分页查看。
3. 在列表第 2 页删除最后一条记录后，页码可能停在超出范围的状态（例如显示 `2 / 1`），需要用户手动点上一页。
4. 员工提交文档新增/修改/删除后，没有页面可以查看自己的待审批变更进度；「文档审批」仅领导可见。
5. 工单状态 `new` 的前端文案是「新建上传」，语义更像文档上传，建议改为「新建」或「待审核」。
6. 编辑工单时把期望完成时间清空，提交后不会清除原值（`expected_at` 为 `null` 时按“未修改”处理）。
7. 流式回答过程中切换会话或点「新对话」，当前流不会自动中止，新会话要等流结束后才加载。
8. 后端短暂不可用时刷新页面，`/auth/me` 失败会被当作未登录并跳转登录页，而不是提示“服务暂时不可用”。
9. 问答输入超过 4000 字时，后端返回统一的「请求参数校验失败」，前端没有明确提示字数上限。
