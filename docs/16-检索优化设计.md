## 1. 背景

首版检索链路上线后，通过合成语料与真实语料两轮评测，得到了一组可以归因的数据。本设计基于这组数据，给出检索侧的完整优化方案。

设计的核心原则是：**每一次改动都必须能被现有评测系统量化，且可独立回滚。**

## 2. 现状诊断

上传文件

       └─ sanitize_text()                 清洗控制字符

| 平均召回率 | 0.918 | 0.951 | 0.958 |

| **引用精确率** | **0.208** | **0.109** | **0.216** |
| **误拒率** | **21.3%** | **13.3%** | **17.3%** |
| 拒答正确率 | 100% | 100% | 100% |
| 平均耗时 | 2416 ms | 2465 ms | 2478 ms |

### 2.4 根因归因

**R1 切分破坏语义（高）**
89.4% 的块从句子中间切开，模型拿到的是"半句话 + 半句话"。这是引用精确率低与误拒率高的共同底层原因。

**R2 结构信息丢失（高）**
`\s+` 压平后，标题、段落、列表、表格全部变成一行。模型无法判断"这一块属于哪一章"，引用也无法展示章节路径。

**R3 单路稠密召回（中）**
只有向量一路。编号、专有名词、错误码类查询缺乏精确匹配能力。当前语料尚可，语料扩展后会放大。

**R4 检索深度与引用展示耦合（高）**
`TOP_K` 同时决定"检索几条""喂给模型几条""引用几条"。实验数据证明：
- k=10 时误拒率从 21.3% 降到 13.3%，说明上下文确实不够；
- 但引用条数翻倍，引用精确率从 0.208 掉到 0.109；
- 换算成绝对数量：每答的相关引用从 1.04 条变成 1.09 条，**检索没变好，只是把噪声也展示出来了**。

**R5 无精排（高）**
5 条候选用余弦分数直接排序，bi-encoder 无法判断细粒度相关性。引用精确率 20.8% 即"5 条里只有 1 条真相关"。

**R6 拒答依赖 prompt（中）**
无阈值。拒答 100% 正确是因为语料干净、不可回答题明显；可回答题误拒 21.3%，是"检索给的证据不足"与"prompt 过严"叠加的结果。

**R7 多轮检索不看历史（中）**
rewritten 实验证明：4 条多轮第二问全部从 1 分变 5 分，改写收益确定。但生产链路未启用。

## 3. 设计目标与约束

### 3.1 目标（以 baseline-v0 为参照）

| 指标 | 现状 | 目标 |
|---|---|---|
| 引用精确率 | 0.208 | ≥ 0.45 |
| 误拒率 | 21.3% | ≤ 8% |
| 拒答正确率 | 100% | ≥ 90% |
| MRR | 0.918 | ≥ 0.95 |
| 轮次通过率 | 77.8% | ≥ 88% |
| 平均耗时（p95） | 2.4 s | ≤ 3.5 s（CPU 环境） |

### 3.2 约束

1. **不引入新中间件**：混合检索用 PostgreSQL tsvector，不引 Elasticsearch。
2. **可回滚**：所有新策略由配置开关控制，关闭后退回当前行为。
3. **可复现**：每次评测运行快照检索配置。
4. **可降级**：精排、改写任一环节异常不得阻断问答。
5. **不改变对外接口语义**：SSE 事件、引用结构保持兼容。

## 4. 目标架构

```
                     ┌────────────────────────────────────────────┐
 query ──► [改写] ──► │ 候选召回                                    │
         （按需）      │  dense  : pgvector cosine  top 30           │──┐
                     │  sparse : tsvector + GIN   top 30           │  │
                     └────────────────────────────────────────────┘  │
                                                                     ▼
                                                          RRF 融合 (k=60)
                                                                     │
                                                                     ▼
                                                            去重 + 相邻合并
                                                                     │
                                                                     ▼
                                                     [精排] bge-reranker-v2-m3
                                                         40 → 重排 → 阈值过滤
                                                                     │
                                                    ┌────────────────┴───────────┐
                                              最高分 < 阈值                  最高分 ≥ 阈值
                                                    │                            │
                                                拒答（无据）              取 final_k=5 → 上下文组装
                                                                                 │
                                                                                 ▼
                                                                           LLM 生成 + 引用
```

关键：**候选池（candidate_k）与最终展示（final_k）彻底分离**。

## 5. 模块设计

### 5.1 解析与切分

#### 5.1.1 设计原则

- 以**结构单元**为切分边界，不以字符数为边界；
- 段落是最小单元，标题是分组单位；
- 表格整体成块，不跨块切分；
- 只有在超长段落内部才按句子切，并允许句子级重叠。

#### 5.1.2 处理流程

```
原始文本
  → 保留换行（去掉 re.sub(r"\s+", " ")）
  → 识别结构单元：
      标题行（# / 第X章 / 数字编号）
      段落（连续非空行）
      列表（- / 1. / 一、）
      表格（连续以 | 开头的行）
  → 按标题层级分组，生成 heading_path
  → 单元合并到目标长度区间
  → 超长段落按句末标点切分
  → 表格单独成块；超过上限时按行切分并重复表头
  → 输出 [{content, heading_path, unit_type, char_count}]
```

#### 5.1.3 参数

| 参数 | 建议值 | 说明 |
|---|---|---|
| `CHUNK_TARGET` | 450 字符 | 目标长度 |
| `CHUNK_MAX` | 700 字符 | 超过则强制切分 |
| `CHUNK_MIN` | 150 字符 | 低于则与相邻同节单元合并 |
| `CHUNK_OVERLAP` | 60 字符 | 仅在段落内句级切分时使用 |
| 表格上限 | 900 字符 | 超过按行切分，重复表头 |

> 中文 450 字符 ≈ 300–400 token，对 BGE-M3 与 reranker 都友好，retrieval 粒度也合适。

#### 5.1.4 伪代码

```python
def structure_chunk(text: str, cfg) -> list[Chunk]:
    units = parse_units(text)          # 标题/段落/列表/表格
    chunks, buf, heading = [], [], []
    for u in units:
        if u.is_heading:
            flush(buf); heading = update_heading_path(heading, u)
            continue
        if u.is_table:
            flush(buf)
            chunks += split_table(u, cfg)   # 超长表格按行切
            continue
        if len(buf_text(buf)) + len(u.text) > cfg.max:
            flush(buf)
            if len(u.text) > cfg.max:
                chunks += sentence_split(u.text, cfg)
                continue
        buf.append(u)
    flush(buf)
    return chunks
```

#### 5.1.5 验收

| 指标 | 现状 | 目标 |
|---|---|---|
| 结尾为标点的块占比 | 10.6% | ≥ 85% |
| 含换行的块占比 | 0% | ≥ 90% |
| 达到上限的块占比 | 90.6% | ≤ 15% |
| heading_path 覆盖率 | 0 | 100% |
| 检索命中率 | 96.0% | 不回退 |
| **引用精确率** | 0.208 | ≥ 0.32 |

> 切分是第一步，预期单独就能把引用精确率抬到 0.3 以上——因为相关块不再被"半句话"污染。

### 5.3 混合检索

#### 5.3.1 分词与索引

中文分词在 **Celery worker 内用 jieba** 完成，写入时分词结果以空格拼接存进 `content_tsv`：

```sql
ALTER TABLE document_chunks ADD COLUMN content_tsv tsvector;
CREATE INDEX ix_chunks_tsv ON document_chunks USING gin(content_tsv);

-- 写入时（Python 侧先 jieba.cut）
-- to_tsvector('simple', ' '.join(jieba.cut(content)))
```

选择应用侧分词而非 PG 扩展的原因：无需在数据库容器安装 zhparser/pg_jieba，分词规则可随代码版本管理。

**风险**：jieba 版本升级导致分词漂移，需全量重刷。因此把分词器版本写入 `chunk.meta`，变更时记录并重刷。

#### 5.3.2 融合算法

两路各自取 `candidate_k = 30`，用 RRF 融合：

```
score(d) = Σ_i 1 / (k + rank_i(d)),  k = 60
```

RRF 只看排名不看分数，天然规避两路分数量纲不同的问题。

#### 5.3.3 SQL 草案

```sql
WITH dense AS (
  SELECT c.id, ROW_NUMBER() OVER (ORDER BY c.embedding <=> :vec) AS rank
  FROM document_chunks c JOIN documents d ON d.id = c.document_id
  WHERE d.is_deleted = false AND d.source = :source
  ORDER BY c.embedding <=> :vec
  LIMIT 30
), sparse AS (
  SELECT c.id, ROW_NUMBER() OVER (
           ORDER BY ts_rank_cd(c.content_tsv, plainto_tsquery('simple', :q)) DESC) AS rank
  FROM document_chunks c JOIN documents d ON d.id = c.document_id
  WHERE d.is_deleted = false AND d.source = :source
    AND c.content_tsv @@ plainto_tsquery('simple', :q)
  LIMIT 30
), fused AS (
  SELECT id, SUM(1.0 / (60 + rank)) AS score
  FROM (SELECT * FROM dense UNION ALL SELECT * FROM sparse) t
  GROUP BY id
)
SELECT c.*, f.score FROM fused f JOIN document_chunks c ON c.id = f.id
ORDER BY f.score DESC LIMIT 40;
```

`source` 过滤为后续隔离 RGB 语料预留。

### 5.4 精排

#### 5.4.1 服务接口

在现有 embed 服务中新增：

```
POST /rerank
{ "query": "...", "passages": ["...", "..."], "batch_size": 16 }
→ { "scores": [0.93, 0.12, ...], "model": "BAAI/bge-reranker-v2-m3" }
```

放在 embed 容器的理由：模型加载、设备选择、超时策略统一管理，API 服务保持无状态。

#### 5.4.2 处理细节

| 项 | 设计 |
|---|---|
| 候选数 | rerank 前 40（可配置） |
| 文本截断 | passage 截断至 512 token |
| 批大小 | 16 |
| 超时 | 800 ms |
| 降级 | 超时/异常 → 回退 RRF 排序，记录告警 |
| 输出 | sigmoid 后的 0–1 相关性分数 |

#### 5.4.3 CPU 性能预警

`bge-reranker-v2-m3` 约 568M 参数。**实施前必须压测**：40 条候选在 CPU 上的单次耗时。

若超过 1 秒，按下列顺序降级：

1. 候选降到 20
2. passage 截断到 256 token
3. 改用 `bge-reranker-base`
4. 启用 GPU overlay

#### 5.4.4 阈值

```
top1_score < RERANK_THRESHOLD  → 直接拒答，不调用 LLM
```

阈值来自评测数据的分布标定，**不预设固定值**。标定方法见 8.3。

### 5.5 查询改写

#### 5.5.1 触发条件

仅在满足以下任一条件时改写：

- 会话轮次 > 1 且问题包含指代词（它 / 这个 / 那个 / 上面 / 刚才）
- 问题长度 < 8 字
- 上一轮检索最高分低于阈值

#### 5.5.2 设计

- 复用评测侧已有实现（`eval_judge.rewrite_question`），抽为公共模块；
- 只改写**检索用问题**，生成仍用原始问题 + 历史；
- 改写失败回退原问题，记录 warning；
- Redis 缓存：key = `md5(question + last_turn)`，TTL 24h。

### 5.6 上下文组装

精排后取 `final_k = 5`，组装前处理：

1. **去重**：按 `content_hash` 去重；
2. **相邻合并**：同一文档、序号相邻的块合并为一段，避免上下文被切碎；
3. **预算控制**：总 token 不超过 3000，超出按分数从低往高淘汰；
4. **顺序**：按文档 + 块序输出（便于模型阅读），但引用编号按分数降序；
5. **引用映射**：仅将实际进入上下文的块生成引用，不再包含被淘汰的候选。

### 5.7 拒答策略

三级判据，任一满足即拒答：

| 级别 | 判据 | 说明 |
|---|---|---|
| L1 | 候选集为空 | 极端情况 |
| L2 | `top1_rerank_score < threshold` | 主判据 |
| L3 | 精排后有效块数为 0 | 阈值过滤后为空 |

回答侧保留 prompt 约束作为最后一道防线。

| 环节 | 目标耗时 | 降级策略 |

## 8. 评测设计

### 8.1 从文档级升级为块级

当前 `required_document_ids` 是文档级，85 块取 5 时已经饱和（命中率 96%–100%），无法反映改进。

建议：

- `eval_turns` 新增 `required_chunk_hashes jsonb`（用内容指纹而非自增 ID，重刷切分后仍可匹配）；
- 指标增加块级 `recall@k`、`nDCG@5`；
- 文档级指标保留，用于观察退化。

### 8.2 指标分层

| 层 | 指标 | 用途 |
|---|---|---|
| 召回 | recall@5 / @20 / @40 | 判断候选池是否够 |
| 排序 | MRR、nDCG@5 | 判断精排是否有用 |
| 引用 | citation precision / recall | 判断展示是否干净 |
| 生成 | 回答分、误拒率 | 判断端到端效果 |
| 拒答 | 拒答正确率、误拒率 | 阈值调优 |
| 性能 | p50 / p95 延迟 | 上线门槛 |

### 8.3 阈值标定方法

1. 用"混合召回 + 精排、阈值关闭"跑一次全量；
2. 导出每轮 `top1_rerank_score`，按 `expected_type` 分为两组；
3. 画两组分布，找分离点：
   - 有清晰间隙 → 取间隙中点；
   - 无间隙 → 记录结论，改用"分位数 + 回答忠实度"组合判据。

### 8.4 实验矩阵

| 运行 | 配置 | 目的 |
|---|---|---|
| baseline-v0 | 现状 | 参照 |
| exp-topk10 | k=10 | 候选池收益（已完成） |

## 9. 实施计划

| 阶段 | 内容 | 预估 | 验收 |
|---|---|---|---|
| S1 | 结构化切分 + 块元数据 + 全量重刷 | 1.5–2 天 | 断句率 ≤15%，引用精确率 ≥0.32 |
| S2 | 混合检索 + RRF + candidate_k 拆分 | 2–3 天 | 编号类子集 recall@20 提升，延迟 +30ms 内 |
| S3 | 精排 + 阈值 + 降级 | 2–3 天 | MRR ≥0.95，引用精确率 ≥0.45，误拒 ≤8% |
| S4 | 查询改写 | 1 天 | 多轮子集提升，单轮不退化 |
| S5 | 上下文组装 + 引用后处理 | 1 天 | 引用精确率再 +5pp |

**建议顺序**：S1 → S3 → S2 → S4 → S5。

理由：实验数据显示瓶颈是"块质量 + 排序"。先把切分和精排做好，收益最大；混合检索在当前 85 块规模收益有限，应在语料扩张后再做（但代码结构应提前预留）。

## 10. 风险与回滚

| 风险 | 影响 | 应对 |
|---|---|---|
| reranker CPU 延迟过高 | 体验不可用 | 先压测；候选降级 / 换小模型 / GPU |
| 切分重刷导致评测用例失效 | 指标不可比 | 块级标注用内容指纹；重刷后重跑基线 |
| jieba 版本漂移 | 关键词召回变化 | 记录版本；变更时全量重刷 |
| 阈值过严 | 误拒上升 | 阈值可配置，按评测标定 |
| 精排服务故障 | 问答受阻 | 超时降级到 RRF 排序 |
| 指标饱和 | 无法判断改进 | 块级标注 + 分层指标 |

所有新策略均通过 `RetrievalConfig` 开关控制，关闭即回到 baseline-v0 行为。

### 12.3 S3 精排

首次运行（run `2a2f1b36`）配置为 `rerank_top_n=20`、超时 10 秒。事后核对发现**大量请求超时降级**：榜首分数集中在 0.016，正好等于 RRF 的 1/61，说明精排没有真正执行。该次结果作废。

修正后：超时 30 秒、`rerank_top_n=10`，实测单条候选约 0.5 秒，整体精排约 5 秒。

| 指标 | S2 | S3（有效） |
|---|---|---|
| 通过率 | 84.0% | 84.0% |
| 误拒率 | 13.3% | **10.7%** |
| MRR | 0.948 | **0.982** |
| 平均召回 | 0.938 | 0.942 |
| 引用精确率 | 0.221 | 0.223 |
| 平均分 | 4.29 | 4.35 |
| 平均耗时 | 2203 ms | 7196 ms |

结论：精排的收益体现在**排序质量（MRR）与误拒率**，通过率持平是因为剩余失败集中在跨文档与多轮，与排序无关。

**CPU 性能结论**：`bge-reranker-v2-m3` 在 CPU 上约 0.5 秒/条（300 字符）。候选 10 条约 5 秒，20 条约 10 秒。截断到 128 字符可降到 1.4 秒/10 条，但会丢失块内后段信息。上线前必须二选一：启用 GPU，或改用 `bge-reranker-base` 并限制候选数。

### 12.4 S4 查询改写

在 S3 有效配置基础上启用 `rewritten` 模式（多轮第二问用历史改写检索问题）。首次运行（run `bc670bcb`）受同一超时问题影响，作废；重跑结果：

| 指标 | S3（有效） | S4（有效） |
|---|---|---|
| 通过率 | 84.0% | **87.7%** |
| 误拒率 | 10.7% | **6.7%** |
| MRR | 0.982 | 0.982 |
| 平均分 | 4.35 | **4.47** |
| 平均耗时 | 7196 ms | 7113 ms |

逐条比对，状态变化 5 轮：3 条多轮第二问由失败转通过（住宿与招待、资产赔偿、餐费口径，分数 1→4/5），1 条多轮第二问由通过转失败（会议室指代，5→1），1 条单轮题波动（与改写无关）。

结论：改写对多轮指代问题的收益是确定的（4 条中 3 条修复），建议在开启精排的前提下默认启用。

### 12.5 S5 阈值标定

对 S3 有效运行的精排榜首分数做分布分析：

| 类型 | 条数 | 最小 | 平均 | 最大 |
|---|---|---|---|---|
| 可回答 | 75 | 0.013 | 0.804 | 0.996 |
| 不可回答 | 6 | 0.015 | 0.488 | 0.960 |

**分布严重重叠**：3 条不可回答题的榜首分数分别为 0.015、0.068、0.095，另 3 条为 0.896、0.896、0.960。

高分那三条是典型的"检索相关但无答案"：例如"海外出差住宿标准"会命中差旅章节，"数据库变更流程"会命中提到该规范的文档。cross-encoder 只能判断相关性，无法判断"是否包含答案"。

按阈值 0.2 过滤：

- 可回答题中 73/75 在 0.2 以上，强制拒答会误伤 1 条已通过用例；
- 不可回答题中 3 条低于 0.2（本来就已被 prompt 正确拒答），3 条高于 0.2 拦不住。

**结论：基于精排分数的绝对阈值在当前语料上不可用。** 实测阈值 0.2 的运行：

| 指标 | S4 | S5（阈值 0.2） |
|---|---|---|
| 通过率 | 87.7% | **76.5%** |
| 误拒率 | 6.7% | **14.7%** |
| 拒答正确率 | 100% | 100% |
| 平均分 | 4.47 | 4.08 |

不可回答题的拒答正确率没有提升（本来已是 100%），可回答题却被强制拒答了 11 条。**阈值只带来损失，没有收益。**

若需进一步收紧拒答，应增加**答案忠实度校验**（生成后核对每个结论是否有引用片段支撑），而不是检索分数阈值。

### 12.6 最终结论

| 阶段 | 相对上一阶段的主要收益 | 是否默认启用 |
|---|---|---|
| S1 结构化切分 | 通过率 77.8%→81.5%，误拒 21.3%→16.0%，MRR 0.918→0.948 | 是 |
| S2 混合检索 | 通过率 81.5%→84.0%，误拒 16.0%→13.3% | 是 |
| S3 精排 | MRR 0.948→0.982，误拒 13.3%→10.7%；延迟 2.2s→7.2s | 视硬件（GPU 或小模型） |
| S4 查询改写 | 通过率 84.0%→87.7%，误拒 10.7%→6.7% | 是 |
| S5 分数阈值 | 通过率 87.7%→76.5% | 否 |

最终配置（CPU 环境）：结构化切分 + 混合检索 + 查询改写，精排默认关闭；若上 GPU，则打开精排，可再提升 MRR 与误拒率。

遗留问题：文档级评测指标已饱和（命中率 98.7%），无法进一步区分改进，需要块级标注；跨文档类用例仍是主要失败来源（占失败的一半）。
