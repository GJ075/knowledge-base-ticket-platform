# 14 工程化基建设计

> 状态：实施中

> 关联文档：[16 检索优化设计](16-检索优化设计.md)、[12 评测系统设计](12-评测系统设计.md)、[07 开发阶段与验收](07-开发阶段与验收标准.md)

## 1. 背景

检索优化完成后，系统具备了一条完整、可配置的检索管线：结构化切分、混合召回、RRF 融合、精排、组装。同时引入了三类新增风险：

1. **分支变多**：`hybrid_enabled`、`rerank_enabled`、`rerank_threshold`、降级路径，任意组合都可能出现行为差异。
2. **反馈变慢**：验证一次改动需要跑 81 轮评测，20–40 分钟，且指标自带 2–3% 随机噪声。
3. **参数变多**：配置错误不再一定表现为崩溃，而是"安静地做错事"。

本文档定义支撑这套系统的工程地基，目标不是修某一个问题，而是让后续每一次改动都具备：**快速反馈、可定位失败、防止退化**。

## 3. 设计原则

### 3.1 测试金字塔，而不是"补测试"

```
        ┌─────────────┐
        │ L3 端到端评测 │  81 轮 · 20–40 分钟 · 人工判读
        ├─────────────┤
        │ L2 集成测试  │  数据库/服务依赖 · 秒级 · 少量
        ├─────────────┤
        │ L1 纯函数单测 │  无 IO · 毫秒级 · 大量
        └─────────────┘
```

原则：**能用 L1 表达的，绝不放到 L3**。

理由：L3 一次运行 20 分钟，且结果受 LLM 随机性影响；L1 一次全跑不到 1 秒，失败信息精确到断言。把"融合顺序对不对"这种确定性问题交给 L3，等于用体温计量身高。

### 3.2 纯函数优先

代码已经具备这个条件：

| 模块 | 纯函数 | 依赖 |
|---|---|---|
| `chunking.py` | `parse_units` / `split_sentences` / `_split_table` / `structure_chunks` | 仅 `get_settings()` 提供默认参数 |
| `retrieval.py` | `fuse_rrf` / `dedupe` / `merge_adjacent` / `within_budget` | 无 |
| `document_metadata.py` | `extract_metadata` | 无 |

**设计约束**：新增检索逻辑时，优先写成"输入列表 → 输出列表"的纯函数，把 IO（查库、调模型）留在最外层的 `search()`。这样逻辑永远可测。

### 3.3 不变量优于文档

文档会过期，校验不会。凡是"这两个参数不能同时这样配"的规则，一律写进 `__post_init__`，让非法配置在构造时就失败。

**fail-fast 优于静默降级**：已经出现过一次教训——`rerank_threshold>0` 但 `rerank_enabled=false` 时，系统拿 RRF 分数（≈0.016）和阈值比较，静默过滤掉所有结果。如果当时有校验，这个配置根本构造不出来。

### 3.4 降级必须可观测

降级本身是正确设计（精排超时不应阻断问答），但降级必须留下痕迹：

- 日志 warning（已加）
- 计数指标（后续）
- 返回结果中带 `origin`，可判断是否走了降级路径

## 4. 测试分层设计

### 4.1 L1：纯函数单测（本次实施）

目录：

```
server/tests/
├── conftest.py               # 公共构造器
├── test_chunking.py          # 切分规则
├── test_retrieval_units.py   # 融合、去重、合并、预算
├── test_config_validation.py # 配置不变量
└── test_document_metadata.py # 元数据提取
```

#### test_chunking.py

| 用例 | 断言点 | 为什么重要 |
|---|---|---|
| 标题不跨块 | 每块的 `heading_path` 以最近的标题结尾 | 引用定位与上下文可读性 |
| 章节切换会冲刷 | 两个章节产生两块，且内容不混 | 防止一节内容被拆到两节 |
| 表格整块保留 | 含 `\|` 的连续行只出现在一块里 | 表格被切断会丢列语义 |
| 超长表格切分 | 每块都包含表头 | 无表头的半张表无法理解 |
| 超长段落按句切 | 每块以句末标点结尾 | 杜绝"断在半句话" |
| 单句超长硬切 | 输出长度 ≤ max，且不丢内容 | 防御病态输入 |
| 短块合并 | 文档头（<min）并入下一块 | 避免 64 字碎片进入检索 |
| 内容去重 | 相同内容只保留一次 | 防止 top-k 被重复块占用 |
| 换行保留 | 块内仍含 `\n` | 结构信息不丢失 |

#### test_retrieval_units.py

| 用例 | 断言点 |
|---|---|
| RRF 双路优先 | 两路都命中的块排第一 |
| RRF 单路靠后 | 只在一路出现的块排在双路之后 |
| RRF 空输入 | 返回空列表，不抛异常 |
| 去重 | 相同 `content_hash` 只保留首条 |
| 相邻合并 | 同文档、index 连续 → 合并为一条 |
| 非相邻不合并 | index 差 2 不合并 |
| 跨文档不合并 | 不同 document 不合并 |
| 超长不合并 | 合并后超过 1200 字则拆开 |
| 预算控制 | 超出预算的块被跳过 |

#### test_config_validation.py

| 用例 | 期望 |
|---|---|
| 阈值 > 0 但未开精排 | `ValueError` |
| `final_k > fused_k` | `ValueError` |
| `candidate_k < final_k` | `ValueError` |
| 默认配置 | 通过 |
| 评测参数合并非法值 | API 返回 422，而非静默运行 |

### 4.2 L2：集成测试（后续）

### 4.3 L3：现有评测（保留）

`RAG 回归集 v2` 继续作为慢验证，但**不是每次提交都跑**，只在阶段性改动后跑一次。它是"验收尺"，不是"开发反馈"。

## 5. CI 设计

### 5.1 流水线

```
push / PR
   ├─ job: api
   │    1. pip install -r requirements-dev.txt   （缓存）
   │    2. ruff check .                          （约 2s）
   │    3. pytest -q                             （约 3s）
   └─ job: web
        1. npm ci                                （缓存）
        2. tsc --noEmit                           （约 30s）
```

目标：**3 分钟内给出结论**。不跑构建、不跑评测、不起数据库——那些放到发布流程。

### 5.2 门禁规则

| 检查 | 失败即阻断 |
|---|---|
| ruff（E9/F：语法与未定义名） | 是 |
| pytest | 是 |
| tsc --noEmit | 是 |

不引入格式检查（black/prettier），避免在现有代码上制造大量无意义 diff。

### 5.3 为什么不用 git hook 代替

本地 hook 可以被 `--no-verify` 绕过，也无法保证所有环境一致。CI 是唯一可靠的记录。本地只提供 `make check` 一键脚本，作为习惯而非强制。

## 6. 配置校验设计

### 6.1 不变量清单

| 规则 | 理由 |
|---|---|
| `final_k ≤ fused_k` | 展示数不能超过候选池 |
| `candidate_k ≥ final_k` | 单路召回至少要能覆盖展示数 |
| `rerank_top_n ≥ final_k` | 精排池至少要能选出展示数 |
| `rerank_threshold > 0` ⇒ `rerank_enabled` | 否则拿 RRF 分数比阈值，结果全被过滤 |
| `0 ≤ rerank_threshold ≤ 1` | 精排输出已归一化到 [0,1] |
| `context_token_budget ≥ 500` | 过小会导致上下文为空 |
| `chunk_min ≤ chunk_target ≤ chunk_max` | 切分参数自洽 |

### 6.2 错误传播

```
RetrievalConfig.__post_init__  → ValueError
        ↓
Settings model_validator       → 启动时失败（fail fast）
        ↓
eval_service._merge_retrieval_config → AppError(422)
```

三层各管一段：领域对象管自身一致，进程配置管启动，API 管入参。

## 7. 目录与命名约定

```
server/
├── app/                 # 生产代码
├── tests/
│   ├── conftest.py      # 只放构造器，不放测试
│   └── test_<module>.py # 与被测模块同名
├── requirements.txt     # 运行时
├── requirements-dev.txt # 测试与检查（-r requirements.txt）
└── pyproject.toml       # ruff / pytest 配置
.github/workflows/ci.yml
```

命名：`test_<被测模块>.py`，测试函数 `test_<行为>_<条件>`，例如 `test_merge_adjacent_keeps_gap`。

## 8. 演进路线

| 阶段 | 内容 | 触发条件 |
|---|---|---|
| 现在 | L1 单测 + CI + 配置校验 | 立即 |
| 下一步 | 检索结构化日志 + 降级计数 | 上线前 |
| 之后 | L2 数据库集成测试（service 容器） | 检索 SQL 再改时 |
| 之后 | 前端 E2E（Playwright）覆盖上传→问答 | 页面再改时 |

## 9. 验收标准

1. `pytest` 在无数据库、无模型服务环境下全部通过，耗时 < 5 秒。
2. 非法配置在构造时抛出 `ValueError`；API 入口返回 `422`。
3. CI 在 3 分钟内完成 api 与 web 两个 job。
4. 新增检索逻辑时，能明确回答"这条逻辑属于 L1 还是 L3"。
