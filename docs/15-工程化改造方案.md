# 15 工程化与可维护性改造方案

> 日期：2026-11-11
> 关联：[14-工程化问题清单](14-工程化问题清单.md)（问题与证据）、[02-总体架构设计](02-总体架构设计.md)
> 目标：把系统从「能跑」提升到「可重复、可观测、可回滚」。

## 1. 成熟度评估

采用四级模型：

| 级别 | 特征 |
|---|---|
| L1 能运行 | 功能可用，靠人工操作与记忆维护 |
| L2 有规范 | 目录、命名、迁移、错误码有约定 |
| L3 可重复 | 自动化检查与测试、可重现构建与发布、可观测 |
| L4 可演进 | 度量驱动、快速回滚、容量与成本可控 |

当前处于 **L1 与 L2 之间**：已有分层目录、迁移、统一错误码、JSON 日志、固定依赖版本，但缺少自动化保障与运行可观测性。

目标：**L3**。不追求 L4 的重型平台能力，保持模块化单体。

| 维度 | 现状 | L3 目标 | 关键差距 |
|---|---|---|---|
| 架构分层 | router 直接调用巨型 service | api / application / domain / infrastructure 四层 | 事务、查询、校验、序列化混在一起 |
| 领域建模 | 状态机与权限散落在 service | 领域策略独立、可单测 | 工单/文档规则难以复用与验证 |
| 数据治理 | 迁移有编号，无回填规范 | expand/contract、回填可重入、迁移说明 | 0008 未回填索引，运行态与代码漂移 |
| 接口契约 | Pydantic 与 TS 类型双写 | OpenAPI 生成 TS，CI 校验 | 已出现 `retrieval_config` 只在后端 |
| 测试 | 无自动化测试 | 金字塔 + 关键路径 E2E | 状态机、指标、检索融合无护栏 |
| CI/CD | 无 | 四道门 + 分阶段发布 | 合并前无任何自动检查 |
| 可观测性 | JSON 日志，无指标 | 日志贯通 + 指标 + 告警 | 降级无法发现，故障靠猜 |
| 安全 | JWT、RBAC、Cookie | 限流、密钥管理、CSRF、依赖扫描 | 默认密钥、预填密码、无登录限流 |
| 交付 | 手工 compose | 测试环境、发布 tag、回滚演练 | 迁移自动执行、无回滚流程 |
| 前端工程 | 类型严格、零 any | 错误边界、组件分层、E2E | 巨型页面、无 lint、无错误边界 |

## 2. 根因分析

问题清单有 20 多项，根因只有六个：

1. **功能驱动、缺少质量门禁**：每次改动靠人工点页面验证，测试与 CI 缺位，导致问题只能上线后发现。
2. **单层 service 模式在规模增长后失效**：一个 service 同时做查询、校验、事务、状态流转，文件涨到上千行，修改回归面不可控。
3. **配置与契约双写**：`Settings` 与 `RetrievalConfig` 各一份默认值；Pydantic 与 TS 类型各写一遍，漂移不可避免。
4. **缺少发布与迁移流程**：迁移随容器启动自动执行，代码未提交也能部署，运行态、数据库、提交记录三者脱节。
5. **缺少可观测性与降级策略**：稀疏召回、精排失败静默降级，没有指标，评测结果的好坏无法归因。
6. **前端缺少工程约定**：没有 lint、错误边界、组件分层与测试，页面随需求线性膨胀。

## 3. 目标架构

```text
api/v1/*            路由、鉴权依赖、请求/响应模型
    ↓
application/*       用例编排：创建工单、审批变更、执行评测、检索问答
    ↓
domain/*            纯规则：状态机、权限、指标计算、融合与阈值策略
    ↓
infrastructure/*    仓储查询、LLM、Embedding/Rerank、MinIO、Celery
```

约束：

- **router 不写业务**：只做参数解析、依赖注入、调用用例、映射响应。
- **application 不拼 SQL**：查询统一放 `infrastructure/repositories`，便于复用与单测。
- **domain 不依赖框架**：状态机、指标、RRF、阈值策略都是纯函数，可直接单测。
- **tasks 只做适配**：Celery 任务负责建会话、调用 application 用例、记录结果。
- **模块边界**：`auth / documents / tickets / chat / eval / system`，跨模块只能调用对方 application 接口。

### 3.1 拆分优先级

| 现状文件 | 目标拆分 |
|---|---|
| `eval_service.py`（1099 行） | `eval/datasets.py`、`eval/cases.py`、`eval/runs.py`、`eval/permissions.py`、`eval/metrics.py` |
| `ticket_service.py`（1042 行） | `ticket/commands.py`、`ticket/queries.py`、`ticket/state_machine.py`、`ticket/permissions.py` |
| `document_service.py`（895 行） | `document/commands.py`、`document/queries.py`、`document/changes.py`、`document/trash.py` |
| `retrieval.py` | 保留为 `retrieval/` 包：`dense.py`、`sparse.py`、`fusion.py`、`rerank.py`、`config.py` |

拆分不改变对外接口，先加测试再搬代码，避免一次性大重构。

## 4. 关键机制

### 4.1 单一配置源

- 所有可调参数只在 `Settings` 定义一次，带默认值、范围校验（`field_validator`）；
- `RetrievalConfig.from_settings()` 只做映射，不再写默认值；
- 非法配置在启动或创建运行时立即报错，不静默丢弃；
- 评测运行把最终生效配置写入快照，报告展示全量。

### 4.2 契约生成

- FastAPI OpenAPI 作为唯一契约；
- 用 `openapi-typescript` 生成 `web/lib/api-types.ts`；
- CI 重新生成并 diff，不一致即失败；
- 前端只 import 生成类型，`lib/types.ts` 仅保留视图层辅助类型。

### 4.3 迁移规范

- 采用 expand/contract：先加列/索引，再改代码，最后删旧列；
- 回填类迁移必须提供**可重复执行**的脚本，并记录进度与完成标记；
- 迁移说明模板：目的、影响表、回填方式、验证 SQL、回滚方式；
- **禁止容器启动自动迁移**，改为发布步骤显式执行，避免多副本并发迁移。

### 4.4 任务可靠性

- 拆分 `ingest` 与 `eval` 队列，分别部署 worker；
- 设置 `task_soft_time_limit` / `task_time_limit`；
- 长任务使用 `acks_late=True`，失败进死信；
- 评测创建使用幂等键或数据库唯一约束，防止重复运行；
- 任务日志携带 `request_id`，与 API 日志串联。

### 4.5 错误与降级

统一错误分类：

| 类别 | 示例 | 处理 |
|---|---|---|
| 用户错误 | 参数非法、状态不允许 | 4xx，返回明确错误码 |
| 依赖错误 | embedding、LLM、MinIO 超时 | 降级或 503，记录指标 |
| 内部错误 | 未预期异常 | 500，记录堆栈与 request_id |

降级必须同时满足三点：**有日志、有指标、评测报告标注**。否则宁可失败，也不要静默给出低质量结果。

### 4.6 可观测性

最低指标集：

- HTTP：QPS、P50/P95 延迟、4xx/5xx 比例；
- 检索：召回耗时、稀疏召回命中数、精排耗时、过滤后条数；
- LLM：首 token 延迟、失败率、超时次数；
- 队列：各队列深度、任务耗时、失败数；
- 评测：运行时长、通过率、降级次数。

实现：`prometheus-fastapi-instrumentator` + 自定义计数器，暴露 `/metrics`；compose 里加 Prometheus/Grafana 作为可选 profile。

### 4.7 安全基线

- 启动校验 `JWT_SECRET` 非默认值、长度足够；
- 登录按 IP + 用户名限流，连续失败锁定；
- 移除登录页预填密码，种子账号首次登录强制改密；
- 生产启用 CSRF token 或 BFF；
- CI 增加 `pip-audit`、`npm audit`。

### 4.8 前端工程

- `app/error.tsx`、`not-found.tsx`、`loading.tsx` 覆盖全局；
- 抽取 hooks：`useSelection`、`useBatchAction`、`usePollingQuery`；
- 组件分两层：`components/ui`（无业务）与 `components/<domain>`（领域组件）；
- 巨型页面按「列表 / 详情 / 表单」拆子组件，单文件控制在 300 行内；
- 加 eslint + prettier，接入 CI；
- a11y 基线：所有输入有 label，表格有 caption，按钮有 aria-label。

## 5. 测试策略

按投入产出排序，不追求覆盖率数字：

| 层级 | 范围 | 工具 | 目标 |
|---|---|---|---|
| 单元 | 状态机、权限策略、指标计算、RRF/阈值、配置合并 | pytest | 领域规则 ≥ 80% |
| 集成 | 仓储查询、迁移、API + 真实 PostgreSQL/MinIO | pytest + httpx + compose test profile | 核心接口全覆盖 |
| E2E | 登录、问答、文档审批、工单流转、评测运行 | Playwright | 5 条主路径 |

集成测试使用独立 compose profile（独立数据库与桶），不污染开发数据。

## 6. 交付流程

1. 小步提交，单 PR 不超过 400 行；
2. CI 四道门：`ruff check`、`tsc --noEmit`、`pytest`、`next build`；
3. PR 模板包含：变更说明、验证方式、迁移与配置影响、回滚方式；
4. 发布打 tag，发布记录写明迁移编号与回滚命令；
5. 每次涉及迁移的发布，先在本地或测试环境演练一次回滚。

## 7. 分阶段计划

| 阶段 | 时间 | 交付物 | 退出标准 |
|---|---|---|---|
| 0 止血 | 1–2 天 | 清理临时文件、轮换 JWT、提交 v2、CI 骨架 | 合并即跑 lint/typecheck/build |
| 1 修 P0 | 3–5 天 | 阈值修复、0008 回填流程、评测策略选择、文档重编号、队列拆分、安全基线 | P0 清单全部关闭 |
| 2 结构治理 | 1 周 | 三大 service 拆分、仓储层、N+1 与索引、统一降级日志、错误边界 | 单文件 ≤ 400 行，核心查询 ≤ 3 次 |
| 3 契约与前端 | 1 周 | OpenAPI 生成类型、组件分层、E2E 主路径 | 类型零手写漂移，E2E 通过 |
| 4 可运维 | 1 周 | 指标告警、备份恢复、保留策略、发布回滚演练 | 5 分钟内定位一次失败，回滚演练成功 |

## 8. 度量指标

| 指标 | 当前 | 目标 |
|---|---|---|
| 变更前置时间 | 无统计 | < 1 天 |
| 变更失败率 | 无统计 | < 15% |
| 平均恢复时间 MTTR | 无统计 | < 30 分钟 |
| 自动化测试数 | 0 | 主路径全覆盖 |
| 合并前自动检查 | 0 项 | 4 项 |
| 迁移回滚演练 | 未做过 | 每次涉及迁移必做 |

## 9. 取舍与反过度设计

- **保持模块化单体**：不拆微服务、不引服务网格；当前瓶颈是质量与可观测性，不是吞吐。
- **不引 Elasticsearch**：PostgreSQL + 分词 tsvector 已能满足当前数据量，先解决回填与评测，再评估。
- **不追求全仓覆盖率**：优先领域规则与核心路径。
- **重构以测试为护栏**：没有测试先补测试，再动结构。
- **不为假设需求加抽象**：拆分以现有复杂度为依据，不预建泛化框架。

## 10. 立即可做的十个 PR

1. `.gitignore` 补 `*.tmp`、`cookies*`、`.vscode/`；删除临时文件；轮换 `JWT_SECRET`。
2. 提交当前检索 v2 与 0008 迁移，打 tag，形成可回滚基线。
3. 搭 CI：ruff、tsc、pytest（先放冒烟）、next build。
4. 修阈值逻辑并补单测：仅精排生效时应用阈值。
5. 迁移 0008 回填说明 + `reindex_all` 幂等与进度输出。
6. 评测页增加策略预设选择与参数校验，运行快照保存配置。
7. Celery 拆分 ingest/eval 队列，设置超时与重试。
8. `list_datasets` / `list_runs` 改聚合查询，消除 N+1。
9. OpenAPI 生成 TS 类型并接入 CI diff。
10. 前端补 `error.tsx` / `not-found.tsx`，加 Playwright 主路径。
